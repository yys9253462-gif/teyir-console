# 订阅交付验证脚本

这里的脚本在**目标测试机**上跑，用真实客户端验证订阅交付的节点
「客户导入后到底能不能用」。

## 为什么必须是真实连接

铁律⑱：**列表里有 ≠ 连得上**。
订阅 JSON 里有 5 个节点、格式正确、密码字段齐全 —— 这些都不代表客户能用。
唯一可信的判据是：用真实客户端连上去，看出口 IP 是不是那台节点。

实测（2026-10-03）就是这么发现问题的：5 个节点里 2 个连不上，
而在面板上看它们「状态正常」。

## verify-5rounds.sh

五轮，每轮一个维度：

| 轮次 | 验什么 |
| :--- | :--- |
| R1 | **交付完整性** —— 订阅里每个节点都能建连并出网（出口 IP 必须是该节点） |
| R2 | **三种格式一致** —— clash / sing-box / uri 解析出的节点集合必须完全相同 |
| R3 | **端口跳跃** —— 客户端走 port hopping 时也能连 |
| R4 | **认证边界** —— 错误密码必须被拒（证明鉴权真的在生效，不是放行一切） |
| R5 | **幂等稳定** —— 同一节点连续连三次都成功（排除偶发） |

跑法（在目标测试机上）：

```bash
bash /root/save-subtoken.sh     # 先把一条订阅的 token 存到 /root/.subtoken
bash /root/verify-5rounds.sh
```

## 这两个脚本自己踩过的坑（都是测试写错，不是功能问题）

**① 客户端语法写错**
hysteria 客户端的端口跳跃是 `host:port,start-end`；
写成 `start:end` 是 **sing-box** 的语法，hysteria 不认。
第一版用 `sed 's/-/:/'` 转换，结果**连基准都失败** —— 一度被误判成
「端口跳跃不可用」，而实际上节点侧的 REDIRECT 规则好得很（nftables 计数器在涨）。

**② 测试时序写错**
固定 `sleep 7` 就 curl。但跳跃模式要逐端口试，握手比普通模式慢，
请求发出去时客户端还没就绪 → 超时 → 假 FAIL。
**必须等客户端自己打印 `connected to server` 再发请求**（脚本里已改成轮询等待）。

教训：**假 FAIL 会浪费大量时间去查一个不存在的功能问题。**
看到失败先分辨是"代码错"还是"断言/测试错"（铁律⑨），
尤其当别的证据（如节点侧计数器）显示功能正常时。
